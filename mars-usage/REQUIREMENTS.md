## 0. 구현 에이전트 작업 방식

이 문서는 특정 도구에 종속되지 않는다. Claude Code, Codex, Cursor 등 어떤 AI 코딩 에이전트에게 맡기든 아래 절차를 따른다. 사용하는 도구가 프로젝트 규칙 파일(예: `CLAUDE.md`, `AGENTS.md`, `.cursorrules`)을 자동으로 읽는다면 §2의 확정 사항 요약과 아래 1~6번 규칙을 그 파일에도 넣어 둔다.

1. 이 문서와 프로젝트 규칙 파일을 먼저 읽는다. **코드를 쓰기 전에 Phase 0 산출물(§16)을 제출하고 확인을 받는다.**
2. Phase가 끝날 때마다 멈추고, 요약·실행 방법·다음 Phase 계획을 보고한 뒤 확인을 요청한다.
3. 문서에 없거나 [미결]인 사항은 임의로 정하지 않는다. 가정을 명시하고 `docs/OPEN_QUESTIONS.md`에 기록한다.
4. 실제 DB 접속정보, 실데이터, 실제 개인정보를 요청·생성·커밋하지 않는다. 가상 데이터만 쓴다.
5. 코드 식별자는 영어, 주석과 문서는 한국어로 쓴다. 커밋 메시지는 Conventional Commits 형식(`타입: 제목`)을 따르되 제목과 본문은 한국어로 쓰고, 본문은 변경 내용을 개조식으로 정리한다. UI 문구는 반드시 i18n 키로 쓴다.
6. **화면을 바꾸면 기능 테스트와 별도로 화면을 직접 확인한다(§15 화면 검증).** 완료 기준에서 벗어난 부분(줄바꿈, 잘림, 겹침 등)을 "사소하다", "목업이니 괜찮다"며 스스로 허용하지 않는다. 고치지 못했으면 보고에 적는다. 보고할 때는 확인한 것(단위 테스트, 콘솔 오류, 화면)과 확인하지 않은 것을 구분해서 쓴다. "오류 없음"을 "화면 확인 완료"처럼 보고하지 않는다.

## 1. 개요와 범위

MARS 관리자 웹사이트는 여러 관리 기능을 모듈로 담는 포털이다. 사용자는 포털 홈에서 모듈을 골라 들어간다.

| 모듈 | 이번 범위 |
|---|---|
| 사용현황 분석 (`usage`) | 전체 구현 (§11) |
| MARS DB 탐색 (`db`) | "준비 중" 자리표시자만 (메뉴, 라우트, 권한). 추후 기능: Procedure/Table을 DB 서버·Database 간 비교 |
| 기타 모듈 | 추가할 수 있는 구조만 확보 (§4 모듈 레지스트리) |

**비범위**: 자체 ID/PW 로그인, 실데이터 연결(담당자가 직접), DB 탐색 기능 구현, 데이터 편집(전 화면 읽기 전용), 모바일 전용 최적화(기본 반응형만), 다크 모드, 화면 밀도 전환, 중국어 UI.

**사용현황 분석의 목적**: MARS 시스템이 실제로 얼마나, 어떻게 쓰이는지 본다. 대시보드로 훑어보고, 클릭해서 기능·사용자 단위까지 내려가는 구조다.

## 2. 확정 사항 요약

| 항목 | 결정 |
|---|---|
| SSO | OIDC. 이름·부서·ID는 토큰 클레임에서 받음. 자체 ID/PW 없음 |
| 권한 | ①메뉴 접근 ②Site 접근, 두 축. IdP 그룹 클레임 → 권한 매핑. 모든 API에서 서버가 검사. "유저별 사용현황"은 별도 권한 |
| Site | 4개 (한국 2, 중국 1, 미국 텍사스 오스틴 1). Site별로 조회하고 섞어 보지 않음 |
| DB 연결 | 백엔드는 중앙 SQL Server의 고정 접속정보만 사용. Site별 Linked Server·DB 매핑으로 `[linked_server].[database].[schema].[SP]` 호출 |
| 시간 | 각 Site DB는 타임존 없는 datetime(현지 시각). "오늘" = 해당 Site 현지 날짜 |
| 휴일 | SP가 날짜별 `is_holiday` + 휴일명을 제공(공휴일 + 회사 휴일). 토·일을 휴일로 가정하지 않음 |
| 언어 | 한국어·영어. 화면 문구는 번역 파일, 부서·기능·휴일명은 SP가 언어별로 제공 + 보충 매핑 파일 |
| 날짜 표시 | 내부·URL·API·CSV는 항상 `YYYY-MM-DD`. 화면 표시 형식은 **언어와 별도 설정**(`YYYY-MM-DD`(기본) / `MM/DD/YYYY` / `DD/MM/YYYY` / 자동, §7) |
| 주 단위 | 통계·WAU·주 라벨·히트맵·요일별 차트는 ISO 주(월~일). **기간 선택 팝업 달력만 일요일 시작**. 주 시작 요일 설정은 두지 않음 |
| 주·월 | ISO 8601 주(월~일). 라벨 `2026-W01`, 월 `2026-06` |
| 기본 기간 | 오늘이 9/29면 작년 9/29 ~ 오늘(포함). 통계에서는 오늘 제외 |
| 기간 지정 | 프리셋은 즉시 조회. 직접 지정은 기간 선택 팝오버에서 **적용**을 눌러야 조회(§9.1) |
| 휴일 제외 | 일별 지표에서 기본 ON. 차트는 방식 B(§9.3) |
| 스택 | Vite + React(프론트), FastAPI(백엔드), MSSQL(SP 호출 방식) |
| 데이터 | 실데이터는 담당자가 직접 연결. 이번엔 일관된 가상 데이터로 견본 제작 |
| 지표 정의 | "사용"·체류시간·부서 기준은 SP가 결정. 앱은 SP 값을 그대로 사용 |
| 테마·밀도 | 테마 6종, **라이트 모드만**. 밀도는 단일(보통), 전환 설정 없음(§8) |

## 3. 기술 스택

**프론트엔드**: Vite, React 18+, TypeScript(strict), React Router, TanStack Query v5, TanStack Table + TanStack Virtual, Apache ECharts(얇은 자체 래퍼), react-aria-components(기간 선택 팝오버, 날짜는 `@internationalized/date`의 `CalendarDate`), react-i18next, Tailwind CSS + CSS 변수 토큰, Vitest + Testing Library, ESLint/Prettier, npm.
- 날짜는 `YYYY-MM-DD` 문자열로만 다루는 자체 유틸을 만든다. `Date` 객체로 타임존 변환하지 않는다. 라이브러리 경계에서는 `CalendarDate`(타임존 없는 날짜)로만 변환한다.
- 화면에 보이는 날짜는 `formatDate`/`parseDateInput` 한 곳에서 날짜 형식 설정(§7)에 따라 변환한다. 컴포넌트에서 직접 서식하지 않는다.
- 폰트는 자체 호스팅한다(사내망에서 외부 CDN이 막힐 수 있음). 한/영은 Pretendard, 한자(중국 Site의 사람 이름 등)는 시스템 CJK 폰트 폴백(`PingFang SC`, `Microsoft YaHei`, `Noto Sans SC`).

**백엔드**: Python 3.11+, FastAPI, pydantic v2, pyodbc(ODBC Driver 18), authlib(OIDC), TTL 캐시(`cachetools` 또는 자체 구현), numpy(가상 데이터), pytest, ruff, uvicorn.

원하는 스택이 다르면 §18에 적어 주세요.

## 4. 아키텍처

```
Browser (React) ──/api──▶ FastAPI ──▶ UsageProvider (인터페이스)
                                      ├─ MockProvider   (DATA_SOURCE=mock)
                                      └─ MssqlProvider  (DATA_SOURCE=mssql)
                                             │ 고정된 중앙 DB 접속정보
                                             ▼
                                      중앙 SQL Server
                                             │ Site에 매핑된 Linked Server로 원격 SP 호출
                                             ▼
                                      선택한 Site의 MSSQL DB
```

**백엔드 규칙**
- 라우터는 Provider 인터페이스만 안다. `MockProvider`와 `MssqlProvider`는 같은 메서드·같은 반환 모델(pydantic)을 갖는다. 실데이터 연결 시 수정 범위는 `MssqlProvider`와 설정뿐이어야 한다.
- 테이블을 직접 쿼리하지 않고 SP만 호출한다. `sp_registry` 한 곳에서 논리 조회별 SP 이름, 고정 조회 유형(`@metric`/`@basis`/`@view`), 허용 파라미터와 결과 모델을 관리한다(§13). Provider 메서드는 논리 조회별로 유지하며 여러 메서드가 같은 통합 SP를 호출할 수 있다.
- 백엔드는 모든 Site에 대해 동일한 중앙 SQL Server 접속정보(`MSSQL_CONNECTION_STRING`)를 사용한다. Site 선택 시 연결 문자열·접속 IP·기본 접속 DB를 바꾸지 않고, §6의 매핑으로 원격 SP의 4부분 이름을 선택한다. 중앙 접속정보는 환경변수로만 관리하고 원격 Site의 인증정보는 중앙 SQL Server의 Linked Server 로그인 매핑으로 관리한다.
- pyodbc는 동기이므로 스레드풀에서 실행한다. 쿼리 타임아웃(`SP_TIMEOUT_SECONDS`, 기본 30)을 둔다.
- **동일 요청 합치기(single-flight)**: 같은 Site·SP·파라미터의 동시 요청은 SP를 한 번만 실행하고 결과를 공유한다.
- **TTL 캐시**: 오늘을 포함하지 않는 범위는 30분, 오늘을 포함하는 범위는 2분(설정값). 키는 (source, site, 호출 대상, 파라미터). 실데이터의 호출 대상에는 Linked Server·DB·스키마·SP를 포함한다.
- **동시 실행 제한**: Site별 세마포어(기본 4). 초과분은 대기하다가 타임아웃 시 429.
- 클라이언트가 연결을 끊었을 때 SP 실행을 중단하지 못할 수 있으므로, 위 캐시·합치기·타임아웃·동시성 제한으로 DB 부하를 막는다.
- 중앙 DB 접속 계정은 필요한 접속 및 Linked Server 로그인 매핑을 사용하도록 구성한다. 원격 Site에 매핑된 계정은 해당 조회 SP의 EXECUTE 권한만 가지며, 앱 계정에는 Linked Server 생성·변경 권한을 주지 않는다. 실제 원격 SP 권한은 각 Site DB에서 검사한다.
- 모든 응답은 `meta`를 포함한다: `site`, `timezone`, `today`(Site 현지 날짜), `from`, `to`, `generated_at`, `source`(`mock`/`mssql`), `cached`.
- 오류는 `{code, message, request_id}` 형식이다. 상태 코드는 400(검증), 401, 403, 429, 504(타임아웃), 502/500이다.

**Linked Server 호출 규칙**

- 백엔드가 중앙 SQL Server 연결에서 `EXEC [linked_server].[database].[schema].[SP]`를 실행하면 중앙 SQL Server가 선택한 Site에 원격 호출을 전달한다. 조회 로직은 각 Site DB에 배포된 SP에서 실행하며 결과를 중앙 서버를 거쳐 반환한다. 중앙 DB에 8개 SP의 복사본이나 Site 분기용 래퍼 SP를 추가할 필요는 없다.
- Site 접근 권한을 먼저 검사한 뒤 서버 설정의 허용 목록에서 `linked_server`, `database`, `schema`를 선택하고, SP 이름은 `sp_registry`에서 선택한다. 이 식별자들은 클라이언트 입력을 그대로 붙이거나 `?` 값 파라미터로 넘기지 않는다. 검증된 설정값만 SQL Server 식별자 규칙에 맞춰 각각 대괄호로 감싸고 내부 `]`를 이스케이프한다. 날짜·조회 유형·사용자 ID 등 **값은 pyodbc 파라미터 바인딩**으로 전달한다.
- 읽기 전용 SP 호출은 `autocommit=True`로 수행하고 명시적 로컬 트랜잭션으로 감싸지 않는다. 향후 트랜잭션이 필요한 호출을 추가할 때는 원격 프로시저의 트랜잭션 승격 및 MSDTC 구성을 별도로 검토한다. 앱이 서버의 트랜잭션 옵션을 임의로 변경하지 않는다.
- 중앙 SQL Server에는 담당자가 Site별 Linked Server, 원격 로그인 매핑, `RPC OUT`을 구성한다. 중앙 서버에서 원격 Site까지의 네트워크·SQL Server용 OLE DB 공급자·연결 설정도 담당자가 확인한다. 백엔드의 ODBC Driver와 중앙 서버의 Linked Server 공급자는 별개다.
- Site별 동시 실행 제한·캐시·타임아웃을 유지한다. 중앙 서버와 원격 서버 간 연결·조회 타임아웃도 함께 확인하며, 특정 Site 오류 시 다른 Site로 대체 조회하지 않는다. 중앙 SQL Server 장애는 모든 Site 조회에 영향을 주므로 통합 부하와 장애 동작을 검증한다.

호출 예시(`LS_KR1`은 가상 Linked Server 이름, 날짜·조회 유형은 설명용 값):

```sql
EXEC [LS_KR1].[MARSPrimeDB].[dbo].[UsageInsights_Daily]
    @metric = 'dau',
    @from_date = '2026-09-01',
    @to_date = '2026-09-30';
```

**프론트엔드 규칙**
- 서버 상태는 TanStack Query만 쓴다. `queryKey`에 모든 파라미터(source 포함)를 넣고, `signal`로 fetch를 취소한다.
- 화면 컴포넌트는 색·문구·수치 서식을 하드코딩하지 않는다. 토큰, i18n, 서식 유틸만 쓴다.
- 기능 모듈은 레지스트리로 등록한다. 모듈 정의에는 `id`, `path`, `labelKey`, `icon`, `requiredPermission`, `siteScoped`, `routes`, `i18nNamespaces`, `subNav`가 있다. 메뉴·라우트·권한 가드는 레지스트리에서 생성한다.

## 5. 인증·권한

**OIDC 로그인**
- 백엔드가 OIDC 클라이언트로 동작하는 BFF 방식을 권장한다: Authorization Code + PKCE, HttpOnly·Secure·SameSite=Lax 세션 쿠키, 토큰은 브라우저에 노출하지 않음. [제안]
- `/login`은 "SSO로 로그인" 버튼만 있는 화면이다. 미인증 접근 시 로그인 후 원래 주소로 복귀한다(`next` 파라미터는 같은 origin의 경로만 허용해서 오픈 리다이렉트를 막는다).
- 세션 만료 시 안내 후 재로그인, 로그아웃 지원.
- 클레임 이름은 설정으로 뺀다: `name`, `department`, `employee_id`, `groups`. 실제 이름은 IdP 사양 확인 후 채운다 [미결].
- 개발용 `AUTH_MODE=mock`: `/login`에서 가상 사용자(전체 관리자 / 한국 Site만 / 유저별 권한 없음 / 권한 없음)를 고른다. 운영 환경에서 mock이 켜져 있으면 앱이 기동을 거부한다.

**권한 모델**

| 권한 키 | 의미 |
|---|---|
| `usage.view` | 사용현황 분석의 집계 화면 |
| `usage.users.view` | 개인 식별 정보 화면: 유저별 순위·상세, 기능 상세의 "상위 사용자" |
| `dbexplorer.view` | MARS DB 탐색 |
| `admin` | 데이터 소스 전환 등 관리 설정 |

- Site 접근은 `site:{siteId}` 형태로 별도 부여한다(`*` = 전체).
- IdP 그룹 → 권한·Site 매핑은 `config/permission_map.yaml`에서 관리한다(예시는 아래). 유효 권한은 소속 그룹 전체의 합집합이다.

```yaml
groups:
  MARS-Admin-All:   { permissions: [usage.view, usage.users.view, dbexplorer.view, admin], sites: ["*"] }
  MARS-Usage-KR:    { permissions: [usage.view], sites: [KR1, KR2] }
  MARS-Usage-Users: { permissions: [usage.users.view], sites: [] }   # 그룹명은 예시. 실제 그룹명으로 교체
```

**적용 규칙**
- **모든 백엔드 엔드포인트가 (권한, Site)를 검사한다.** 메뉴 숨김은 편의일 뿐 보안이 아니다. 공유 링크로 열어도 동일하게 검사한다.
- 프론트는 `useCan(permission, siteId)`로 메뉴와 패널을 숨기고, 라우트 가드로 `/403`을 보여 준다. 403 화면에는 권한 신청 안내 문구/링크를 설정값으로 둔다.
- 접근 가능한 Site가 하나면 Site 선택기는 고정 라벨로 보인다. 하나도 없으면 안내 화면을 보인다.
- **접근 기록** [제안]: `usage.users.view` 엔드포인트 호출마다 (시각, 조회자 ID, Site, 대상 user_id, 엔드포인트)를 구조화 로그로 남긴다. 보관 위치와 기간은 [미결].
- 유저별 화면 상단에 안내 배너를 둔다: "개인별 사용 이력이 포함된 화면입니다. 조회 기록이 남습니다." 문구는 회사 정책에 맞게 교체한다.
- 테스트: 모든 엔드포인트를 권한 × Site 조합(허용, 권한 없음, 다른 Site)으로 검증한다.

## 6. Site·시간 규칙

- `config/sites.yaml`에서 Site를 관리한다: `id`, 이름(ko/en), `timezone`(IANA), `data_start_date`, `linked_server`, `database`, `schema`. Site별 IP·연결 문자열·DB 인증정보는 두지 않는다. 초기 가정값은 `KR1`, `KR2`, `CN1`, `US1`(오스틴, `America/Chicago`)이다 [미결: 실제 ID·이름·Linked Server 매핑].
- 원격 호출 대상 예시는 아래와 같다. `LS_*`는 가상 이름이고 `MARSPrimeDB`·`dbo`는 제시된 이름을 바탕으로 한 가정값이다. 실제 값은 담당자가 연결 전에 확정한다. 매핑은 서버에서만 관리하고 `/sites` API에는 노출하지 않는다.

| Site | `linked_server` | `database` | `schema` |
|---|---|---|---|
| KR1 | `LS_KR1` | `MARSPrimeDB` | `dbo` |
| KR2 | `LS_KR2` | `MARSPrimeDB` | `dbo` |
| CN1 | `LS_CN1` | `MARSPrimeDB` | `dbo` |
| US1 | `LS_US1` | `MARSPrimeDB` | `dbo` |

- Site는 앱 최상위 조건이다. 헤더에 Site 선택기를 두고 경로에 포함한다(`/usage/:siteId/...`). Site를 바꾸면 같은 화면·같은 조건을 유지한 채 그 Site 데이터로 전환한다. 캐시는 Site별로 분리한다.
- **"오늘"은 서버가 `meta.today`로 내려주는 Site 현지 날짜다.** 백엔드는 Site의 `timezone`(zoneinfo)으로 계산한다. 브라우저 시계로 오늘을 판단하지 않는다.
- 프론트는 날짜를 `YYYY-MM-DD` 문자열로만 다룬다. `new Date('2026-09-29')`는 UTC로 해석되어 하루가 밀리므로 금지한다. 날짜 연산은 자체 유틸(문자열 ↔ 연·월·일 정수)로 하고 테스트한다.
- **휴일은 SP가 준 `is_holiday`만 따른다.** 토·일을 가정하지 않는다(중국은 주말 근무일이 있음).
- 헤더에 Site의 타임존과 데이터 기준 시각을 표시한다(§9.9).

## 7. 다국어

- 언어: `ko`, `en`. 기본은 사용자 설정 → 브라우저 언어 → `ko` 순이다. 헤더에 언어 전환을 둔다. 중국어 UI는 이번 범위가 아니지만, 번역 파일 하나를 추가하면 언어가 늘어나는 구조로 만든다.
- 화면 문구는 네임스페이스별 번역 파일(`common`, `usage`, `errors`, `glossary`)로 관리한다. 초안은 구현 에이전트가 쓰고 담당자가 검수한다. 번역 키 누락은 빌드 시 검사한다.
- **날짜 표시 형식은 언어와 분리된 별도 설정이다.** 한국인이 영어 UI를, 미국인이 한국어 UI를 쓰면서도 날짜는 자기 문화권 형식으로 볼 수 있어야 한다.
  - 선택지: **`YYYY-MM-DD`(기본)** / `MM/DD/YYYY` / `DD/MM/YYYY` / 자동
  - 기본값을 `YYYY-MM-DD`로 두는 이유: 사용자 대부분이 한국 Site이고, 같은 화면을 보며 이야기할 때 날짜 표기가 같아야 혼동이 적다. ISO는 해석이 갈리지 않아 다른 지역 사용자도 그대로 읽을 수 있고, 원하면 설정에서 한 번 바꾸면 된다.
  - 자동(직접 골라야 적용됨)은 브라우저 지역(`navigator.languages`)으로 정한다: `ko`·`zh`·그 밖 → `YYYY-MM-DD`, `en-US` → `MM/DD/YYYY`, `en-GB` 등 일/월 순서 지역 → `DD/MM/YYYY`. 웹에서는 Windows 지역 설정을 직접 읽을 수 없으므로 자동이 기대와 다를 수 있고, 그래서 형식을 직접 고르는 선택지를 함께 둔다.
  - 적용 범위: 카드·툴팁·표·차트 축·기간 표시·입력칸 등 화면에 보이는 모든 날짜. 월 라벨도 형식을 따른다(`2026-09` / `09/2026`). **ISO 주 라벨 `2026-W12`는 항상 그대로**다.
  - 시각은 24시간제 `HH:mm`으로 고정한다.
  - **URL, API, CSV, 내부 계산·정렬은 설정과 무관하게 항상 `YYYY-MM-DD`**다. 형식이 다른 사람끼리 링크를 공유해도 같은 기간이 열린다.
  - 세 형식 모두 10자이므로 표 컬럼 폭은 형식과 무관하게 같다.
- 요일은 UI 언어별 짧은 이름(월 / Mon)이다. 숫자는 천 단위 구분을 쓴다.
- 마스터 텍스트(부서명, 기능명, 휴일명)는 SP가 `name_ko`, `name_en`으로 준다(`name_zh`는 예약 컬럼, §13) [제안]. 백엔드가 `config/name_overrides.yaml`(기능 ID/부서 ID → 언어별 이름)을 덮어씌운 뒤 `name_i18n: {ko, en}`으로 내려준다. 값이 비면 선택 언어 → 영어 → 한국어 → ID 순으로 대체한다.
- 사람 이름은 번역하지 않는다. 부서가 비어 있으면(퇴사자 등) "-"로 표시한다.
- 휴일이지만 이름이 없으면(주말 등) "휴일"이라는 번역 문구를 쓴다.
- 지표 설명 문구는 `glossary` 한 곳에서 관리한다(§9.9, 부록 A).

## 9. 공통 규칙

### 9.1 기간

- **C1** 기본 기간은 `from` = 오늘의 1년 전 같은 날짜, `to` = 오늘(Site 현지)이다. 해당 날짜가 없으면(2/29 등) 그 달 말일로 맞춘다(개월 단위도 동일).
- **C2** 프리셋: 30일 / 90일 / 6개월 / **1년(기본)** / 올해(1/1~오늘) / 작년(1/1~12/31).
  - 30일·90일은 `from = 오늘 − N일`이다. 오늘을 빼면 완성된 N일이다.
  - 6개월·1년은 달력 기준으로 같은 날짜까지 거슬러 올라간다.
- **C3** 직접 지정 검증: 시작일 ≤ 종료일, 종료일 ≤ 오늘, 시작일 ≥ Site의 `data_start_date`, 최대 조회 기간 `MAX_RANGE_DAYS`(기본 1100일, [미결]). 위반 시 팝오버 안에 사유를 표시하고 **적용** 버튼을 비활성화한다. 달력에서 범위 밖 날짜는 선택할 수 없게 흐리게 표시한다.
- **C4** 기간과 휴일 제외 옵션은 사용현황 모듈 안에서 탭을 옮겨도 유지되는 **공용 필터**다 [제안].
- **C5** **프리셋 클릭은 즉시 조회**한다. **직접 지정은 기간 선택 팝오버**에서 하고 **적용을 눌렀을 때만 조회**한다(시작일만 바꾼 중간 상태로 조회하지 않는다).
  - 기간 표시(C6)를 누르면 팝오버가 열린다. 구성: 왼쪽 프리셋 목록, 달력 2개월(**일요일 시작**), 시작/종료 입력칸, "N일 선택됨", **취소 / 적용**
  - 달력: 시작일 클릭 → 종료일 클릭으로 범위 선택, 입력칸이 함께 채워진다. ◀ ▶로 월 이동, 연·월 드롭다운으로 큰 폭 이동
  - 입력칸: 설정한 날짜 형식(§7)으로 표시·입력·해석한다(placeholder에 형식 표시). 입력칸에서 ↑↓ 키는 하루씩 이동. 타이핑은 선택지일 뿐 강제하지 않는다.
  - Enter = 적용, Esc·바깥 클릭 = 취소(원래 기간 유지)
  - 기간 표시 옆 **◀ ▶ (이전/다음 기간)** 버튼: 같은 길이로 앞뒤 이동하고 즉시 조회한다. 종료일은 오늘을 넘지 않고, 시작일이 `data_start_date` 이전이 되면 버튼을 비활성화한다.
- **C6** 기간 선택기 옆에 실제 조회 범위를 `2025-09-29 ~ 2026-09-29 (오늘 포함, 집계중)`처럼 표시한다(날짜는 설정 형식).

### 9.2 오늘(집계중) 처리

- **C7** 오늘 행/점에는 "집계중" 배지를 붙인다.
- **C8** 라인 차트: 오늘 점은 본선과 **연결하지 않는다**. 별도 series로 속이 빈 마커 하나만 그린다(선이 갑자기 떨어지는 모양 방지). 캘린더 주·월과 롤링에도 같은 규칙을 적용한다.
- **C9** 평균·최대·최소·합계·이동평균·증감 등 **모든 통계 계산에서 오늘은 제외**한다.
- **C10** 기간 합산형 조회(기능별, 유저별, 부서별, 기간 요약)는 `to`를 `min(to, 어제)`로 잘라서 호출하고, 화면에 "오늘(집계중) 제외"를 표시한다 [제안].

### 9.3 휴일 제외 (일별 지표: DAU, 신규 이용자, 체류시간)

- **C11** 기본값은 "휴일 제외 ON"이다. 헤더의 스위치 하나로 전환한다.
- **C12** **방식 B**: X축은 달력 날짜를 그대로 유지한다. 휴일의 점만 없애고, 앞뒤 평일 점은 선으로 이어 그린다(연휴는 긴 연결선으로 나타남). X축에서 날짜를 제거하거나 선을 끊지 않는다. (ECharts: 휴일 값을 `null`로 두고 `connectNulls: true`)
- **C13** 휴일 포함 모드에서는 휴일 구간에 옅은 배경 음영을 깔고 범례를 표시한다.
- **C14** 평균·최대·최소·이동평균·증감은 휴일 제외 옵션을 따른다. 계산 대상이 하나도 없으면 "-"로 표시한다.
- **C15** **표는 옵션과 무관하게 조회 기간 전체 행을 보여준다.** 휴일 행은 흐리게 처리하고 휴일명 컬럼에 이름을 표시한다.
- **C16** 7일 이동평균: 휴일 제외 ON이면 직전 영업일 7개(표시된 점 기준), OFF면 달력 7일이다. 값이 7개 미만인 초반 구간은 그리지 않는다.
- MAU/WAU와 누적·90/180/365일 카드에는 휴일 제외 옵션이 없다(롤링 값은 매일 존재하고 휴일과 무관).

### 9.4 통계 카드

- **C17** 일별 지표 화면의 카드: 평균(소수 1자리), 최대(날짜 병기), 최소(날짜 병기), 최근값, 이전 기간 대비. 카드 아래에 산정 근거를 작게 표시한다("N일 기준 · 휴일 M일, 오늘 제외").
- **C18** 이전 기간 = 바로 앞의 같은 길이(달력 일수) 기간이다. 이전 기간이 `data_start_date` 이전을 포함하면 "-"로 표시한다.
- **C19** 증감은 ▲▼ + 부호 + 색 + 퍼센트로 표시한다. 0은 "–"이다.
- **C20** 차트를 확대하면 조회 기간 카드 옆에 "선택 구간" 보조 값(같은 지표 정의)을 표시한다.

### 9.5 차트

- **C21** 공용 `ChartFrame`: 제목, 한 줄 설명, 도움말(?), 로딩/에러/빈 상태, 우상단 도구(이미지 저장 P1), 크기 변화 대응.
- **C22** 조회 기간 평균선을 점선 + 값 라벨로 표시한다(C9, C14 규칙 적용). 범례에서 켜고 끌 수 있다.
- **C23** 툴팁 공통 형식: 날짜(설정 형식) + 요일, 휴일이면 휴일명, 값, 필요하면 이전 대비. 화면 밖으로 잘리지 않게 배치한다.
- **C24** **줌** [제안: 마우스 휠 줌 유지, 페이지 스크롤과 충돌하지 않게 조합]:
  - Ctrl(⌘)+휠 = 확대/축소. **일반 휠은 페이지 스크롤이며 가로채지 않는다.** 일반 휠을 돌리면 "Ctrl+휠로 확대" 힌트를 잠깐 보여준다.
  - 차트 하단 범위 슬라이더(미니맵), 드래그로 구간 선택 확대, 터치 핀치
  - 프리셋 버튼 1M/3M/6M/1Y/전체, "초기화" 버튼
  - 설정에서 "휠만으로 줌" 선택 가능
  - 줌 구간은 URL `zoom=YYYY-MM-DD..YYYY-MM-DD`에 반영한다(디바운스, replace 방식).
- **C25** 라인 차트의 Y축은 0에서 시작하도록 고정하지 않고 데이터 범위에 맞춘다(DAU 100~150이 납작해지지 않게). 막대 차트는 0부터 시작한다.
- **C26** 색은 토큰에서 읽는다. 하드코딩하지 않는다.

### 9.6 표

- **C27** 공용 `DataTable`: 가상 스크롤, 고정 헤더, 헤더 클릭 정렬, 행 hover.
- **C28** **숫자 컬럼은 우측 정렬 + `tabular-nums`이고 헤더도 우측 정렬**한다. **숫자 컬럼 바로 다음이 문자 컬럼이면 자동으로 간격을 준다**(`--table-numeric-gap`, 최소 24px). 개별 화면에서 따로 처리하지 않고 `DataTable`이 보장한다.
- **C29** 날짜 컬럼 바로 다음의 요일 컬럼은 간격을 좁게 붙인다.
- **C30** 컬럼 너비는 내용에 맞춘다(min/max 지정). 숫자 컬럼은 예상 최대 자릿수(천 단위 구분 포함, 예: MAU `1,500`)를 기준으로 폭을 확보한다. 긴 텍스트는 말줄임 + 툴팁이다.
- **C31** 일별 표의 기본 정렬은 날짜 내림차순(최신이 맨 위, 오늘은 "집계중" 배지)이다.
- **C32** CSV 다운로드(필수): 표 전체(현재 검색·필터 적용 여부를 버튼 문구에 명시), **UTF-8 BOM**, 헤더는 현재 언어, 숫자는 천 단위 구분 없는 원시값, **날짜는 설정과 무관하게 `YYYY-MM-DD`**, 파일명 `mars_{site}_{metric}_{from}_{to}[_sample].csv`.
- **C33** 빈 표, 로딩(스켈레톤 행), 에러 상태를 지원한다.

### 9.7 URL과 공유

- **C34** 보고 있는 조건은 URL로 복원할 수 있어야 한다. Site와 대상(기능/유저)은 경로에, 나머지는 쿼리스트링에 둔다.
- **C35** 쿼리 파라미터

| 파라미터 | 값 | 기본 | 사용처 |
|---|---|---|---|
| `range` | `30d` `90d` `6m` `1y` `ytd` `lastyear` | `1y` | 공통 (`from`/`to`가 있으면 그쪽이 우선) |
| `from`, `to` | YYYY-MM-DD | – | 공통 |
| `exclude_holidays` | `1`/`0` | `1` | 일별 지표 화면 |
| `ma` | `1`/`0` | `0` | 7일 이동평균 |
| `basis` | `rolling`/`calendar` | `rolling` | MAU/WAU |
| `unit`, `table` | `month`/`week`, `mau`/`wau` | `month`, `mau` | MAU/WAU 표 |
| `sort` | 기능: `users` `views` `delta` / 유저: `days` `views` `menus` | `users` / `days` | 기능별, 유저별 |
| `q`, `dept`, `top` | 검색어, 부서 ID, `10`/`50`/`all` | – , – , `10` | 유저별 |
| `zoom` | `YYYY-MM-DD..YYYY-MM-DD` | – | 차트 |

- **C36** "링크 복사" 버튼: 기본은 상대 프리셋을 고정 날짜(`from`/`to`)로 바꿔서 복사한다(받는 사람이 같은 화면을 봄). "항상 최신 기간으로" 옵션을 켜면 `range`를 유지한다 [제안].
- **C37** 언어, 날짜 형식, 테마, 데이터 소스 같은 개인 설정은 URL에 넣지 않는다. URL의 날짜는 항상 `YYYY-MM-DD`다.
- **C38** 잘못된 파라미터는 앱을 깨뜨리지 않고 기본값으로 대체하며 작은 안내를 표시한다. 권한 없는 Site는 403 화면이다.

### 9.8 데이터 로딩·취소

- **C39** 파라미터가 바뀌면 이전 요청을 abort하고 최신 요청만 반영한다(TanStack Query `signal`). 같은 키의 중복 클릭/렌더는 요청 한 번으로 합쳐진다. 기간 직접 지정은 팝오버의 적용 시점에만 요청한다(C5).
- **C40** 이전 조건의 화면을 유지한 채 로딩 상태를 표시한다(`placeholderData: keepPreviousData`). 카드, 차트, 표는 각각 독립적으로 로딩된다(하나가 느려도 나머지가 먼저 나옴).
- **C41** 로딩 표시: 화면 상단의 얇은 진행 바 + 각 영역 스켈레톤. 진행률(%)은 SP가 알려줄 수 없으므로 표시하지 않는다. 3초 이상 걸리면 "조회 중… N초 경과"와 **취소** 버튼을 보여준다.
- **C42** 오류/타임아웃: 영역 안에 원인 요약 + **다시 시도** 버튼 + request_id를 보여준다. 401은 재로그인, 403은 권한 화면으로 처리한다.
- **C43** `staleTime`은 캐시 TTL에 맞춘다(기본 5분).

### 9.9 UI 문구·설명

- **C44** 문구는 사실 전달형으로 짧게 쓴다. **광고 문구나 슬로건형 표현은 쓰지 않는다.** 예: "일상의 사용 흐름에서 기능과 사용자까지, 한눈에 살펴보세요" ✗ → 페이지 제목 + "그날 MARS 기능 조회를 1회 이상 한 사용자 수" ✓
- **C45** 모든 지표 라벨 옆에 (?) 아이콘을 두고, 클릭/hover 시 `glossary`의 정의를 보여준다(`MetricHelp` 컴포넌트). 정의 원문은 부록 A이다.
- **C46** 헤더 배지 1: `데이터 기준: 2026-09-28까지 집계 · 갱신 09-29 06:10 (Asia/Seoul)`(날짜는 설정 형식, 시각은 24시간제). `UsageInsights_Freshness` 값을 쓰고, 없으면 `meta.today − 1`을 쓴다.
- **C47** 헤더 배지 2: 가상 데이터일 때 항상 `샘플 데이터`를 표시한다(CSV 파일명에도 `_sample`).
- **C48** 기능별 사용자 수의 합은 전체 이용자 수보다 클 수 있다(한 사람이 여러 기능 사용). 해당 화면에 툴팁으로 설명한다.

### 9.10 접근성·브라우저

- 키보드로 모든 조작이 가능해야 한다(포커스 링, 탭 순서). 차트 옆에 같은 데이터의 표가 있으므로 차트는 `aria-label`로 요약만 제공한다.
- 지원 브라우저: 최신 Chrome/Edge [가정, 미결]. 데스크톱 우선, 1024px 미만에서는 사이드바가 드로어로 바뀐다.

## 11. 기능 명세: 사용현황 분석

각 화면은 "제목 + 설명 한 줄 → 필터 → 요약 카드 → 차트 → 표" 순서를 기본으로 한다. 공통 규칙(§9)은 반복하지 않는다.

### 11.1 개요 Overview (P1)

목적: 첫 화면에서 현재 상태를 보고, 카드를 눌러 상세로 내려간다. 필터는 없고 기준은 최근 30일로 고정이다. 별도 SP 없이 §13의 기존 SP 결과를 조합한다.

**카드 6개** (각각 이전 기간 대비 증감 + 미니 추세선, 클릭 시 해당 화면으로 `range=30d`로 이동)
1. 최근 영업일 DAU(날짜 병기) — 최근 30일 영업일 평균 대비 [제안: 어제가 휴일이면 DAU가 낮게 나오는 오해를 막기 위해 "가장 최근 영업일" 사용]
2. MAU(30일 롤링, 어제 기준) — 30일 전 값 대비
3. 고착도 DAU/MAU — 최근 30일 영업일의 일별 (DAU ÷ MAU) 평균
4. 평균 체류시간 — 최근 30일 영업일 평균, 이전 30일 대비
5. 신규 이용자 — 최근 30일 합계, 이전 30일 대비
6. 최근 365일 이용자 — 누적 대비 %

**하단**: 최근 30일 기능 Top 5(사용자 수, 막대 + 링크), 사용자 수 증가 Top 3 기능.

완료 기준
- [ ] 카드 6개가 서로 독립적으로 로딩된다(하나가 느려도 나머지가 먼저 표시).
- [ ] 어제가 휴일이면 DAU 카드가 직전 영업일을 표시하고 날짜를 병기한다.
- [ ] 각 카드 클릭 시 해당 화면으로 이동하며 기간이 30일로 설정된다.

### 11.2 DAU (P0)

**설명 한 줄**: 그날 MARS 기능 조회를 1회 이상 한 사용자 수.
**데이터**: `UsageInsights_Daily(@metric='dau')`. 일별 행에 날짜, 요일, 이용자 수, 휴일 여부, 휴일명이 있다. 규모는 대략 100~150이다.

**구성**
1. 필터: 기간, 휴일 제외 스위치(기본 ON), 7일 이동평균 체크(기본 OFF)
2. 카드: 평균 / 최대(날짜) / 최소(날짜) / 최근값(오늘이 아닌 마지막 값) / 이전 기간 대비(평균 기준)
3. **메인 차트**: 라인 + 조회 기간 평균선. 이동평균 옵션, 휴일 포함 시 휴일 음영, 오늘 단독 점, 줌(§9.5), 툴팁(날짜·요일·휴일명·값)
4. **요일별 평균**(P1): 월~일 막대. 휴일 제외 옵션을 따르며 "휴일이 아닌 날만 집계" 여부를 툴팁으로 설명한다.
5. **데이터 표**: 날짜, 요일, 이용자 수(우측 정렬), 휴일(휴일명). 조회 기간 전체(휴일 제외 옵션과 무관), 최신순, CSV 다운로드.

완료 기준
- [ ] 기본 진입 시 작년 오늘 ~ 오늘, 휴일 제외 ON으로 표시된다.
- [ ] 오늘 점이 선과 연결되지 않고, 카드·평균선에서 제외된다.
- [ ] 휴일 제외 토글 시 X축 위치가 그대로이고 휴일 점만 사라진다. 평균선과 카드 값이 바뀐다. 표는 그대로다.
- [ ] Ctrl+휠 줌, 슬라이더, 드래그 확대, 초기화가 동작하고 일반 휠은 페이지를 스크롤한다.
- [ ] 표에서 숫자가 우측 정렬되고 다음 문자 컬럼과 붙어 보이지 않는다.
- [ ] 링크 복사 후 새 탭에서 열면 같은 기간·옵션·줌으로 열린다.

### 11.3 MAU · WAU (P0)

**설명 한 줄**: 최근 30일(MAU)·7일(WAU) 동안 MARS 기능 조회를 1회 이상 한 사용자 수.
**데이터**: `UsageInsights_ActiveUsers`의 롤링 `@basis='rolling'`(기준일별 MAU·WAU 동시), 캘린더 `@basis='calendar'` + `@unit='W'/'M'`(주/월별). MAU는 1000~1500, WAU는 300~500 규모다.

**구성**
1. 필터: 기간, **기준 토글(롤링 | 캘린더)** — 기본 롤링, MAU·WAU 공통 [제안]. 이 화면에는 휴일 제외 옵션이 없다.
2. **MAU 차트**(메인, 크게)와 **WAU 차트**(작게)를 분리해서 위아래로 배치한다(스케일 차이). 각 차트 위에 카드(평균/최대/최소/최근값/이전 대비)를 둔다. 각각 조회 기간 평균선과 줌을 가진다.
3. **고착도 차트**(P1, 롤링 기준에서만): DAU÷MAU, WAU÷MAU를 % 선 두 개로 표시한다. 이 차트에만 휴일 제외 토글(기본 ON)을 둔다. DAU는 `UsageInsights_Daily(@metric='dau')` 결과와 날짜로 결합한다 [제안].
4. **표**: 롤링은 `기준일 | MAU | WAU` 한 표, 캘린더는 월/주 탭 각각의 표다.

**롤링 기준**
- X축은 기준일(집계 구간의 종료일). 기준일의 값은 그날을 포함한 과거 30일(WAU는 7일)의 고유 사용자 수다.
- 툴팁 예: `2026-09-27 기준 · 최근 30일 (2026-08-29 ~ 2026-09-27) · 1,234명 · 30일 전 대비 ▲ +12 (+1.0%)`. 비교 대상은 N일 전 기준일의 값이다.
- 오늘의 롤링 값은 집계중이므로 단독 점으로 표시하고 통계에서 제외한다.
- 표 컬럼: `기준일 | MAU(30일) | WAU(7일)`. 숫자 컬럼은 우측 정렬이다.

**캘린더 기준**
- 월: 기간 라벨 `2026-06`(날짜 형식에 따라 `06/2026`), 주: ISO 주 `2026-W12`(월~일, 형식과 무관하게 고정). 라벨은 앱이 시작일로부터 계산한다.
- 툴팁: 기간 라벨, 시작일 ~ 종료일, 이용자 수, 직전 기간 대비 증감.
- 표 컬럼: `기간 | 시작일 | 종료일 | 이용자 수`. 이용자 수는 우측 정렬이고 앞 컬럼(날짜)과 겹쳐 보이지 않게 폭을 확보한다.
- 진행 중인 월/주(종료일 ≥ 오늘)는 단독 점(집계중)으로 표시하고 통계에서 제외한다.
- **포함 규칙** [제안]: 조회 기간에 완전히 포함되는 주·월 + (조회 기간이 오늘을 포함할 때) 진행 중인 주·월을 표시한다. 기간 밖의 날짜가 섞인 값이 기간의 값처럼 보이는 것을 막기 위해서다. 표시할 완성된 기간이 없으면 안내 문구를 보여준다.
- 용어: "표시날짜" 대신 **기간(Period)** 이라는 표현을 쓴다.

완료 기준
- [ ] MAU와 WAU가 서로 다른 차트이고 각각 평균선이 있다.
- [ ] 기본은 롤링이며 토글로 캘린더로 전환된다(URL `basis`).
- [ ] 캘린더에서 진행 중인 주·월, 롤링에서 오늘이 본선과 떨어져 있다.
- [ ] 2025-12-29가 포함된 주가 `2026-W01`로 표시되고 툴팁에 시작일·종료일이 나온다.
- [ ] 롤링·캘린더 툴팁이 위 형식을 따른다.

### 11.4 신규·누적 이용자 (P0)

MARS는 가입 개념이 없어 "가입자"를 직접 구할 수 없다. 누적 이용자와 최근 N일 이용자를 함께 보여줘서 실제 이용자 규모를 추정하게 한다. 화면에서는 "가입자" 대신 **"신규 이용자(최초 접속)"** 로 표기한다.

**데이터**: `UsageInsights_UserBase`(누적, 90/180/365일), `UsageInsights_Daily(@metric='new_users')`(일별 신규·누적).

**구성**
1. **카드 5개** (기준일 = 어제, 휴일 제외와 무관): 누적 이용자 / 최근 365일 / 최근 180일 / 최근 90일 이용자 / 휴면 추정 비율(= 1 − 365일 이용자 ÷ 누적). 각 카드에 누적 대비 %를 표시하고 (?)에 "1년 이상 접속 기록이 없으면 휴면으로 보는 기준이며, 더 엄격한 기준으로 90/180일도 함께 본다"를 설명한다.
2. **구성 막대**(P1): 누적을 `최근 90일 / 91~180일 / 181~365일 / 365일 초과`로 나눈 가로 누적 막대 하나. 사용일 기준이 겹치는 창이므로 차이를 구간 값으로 쓴다.
3. 필터: 기간, 휴일 제외 스위치(기본 ON)
4. 요약: 기간 신규 합계(휴일 제외와 무관하게 전체 합계, 오늘 제외), 일평균(휴일 제외 옵션을 따름), 최대일
5. **차트**: 일별 신규 이용자 **막대**(0부터) + 7일 평균선 + 누적 이용자 선(우측 축). 휴일 제외 ON이면 휴일 막대만 숨긴다. 누적선은 실제 값이므로 끊기지 않는다. 오늘 막대는 빗금 패턴 + "집계중"으로 구분한다.
6. **표**: 날짜, 요일, 신규 이용자, 누적 이용자, 휴일(휴일명). 전체 행, 최신순.
7. **집계 시작일 처리**: Site의 `data_start_date` 부근은 기존 사용자가 한꺼번에 신규로 잡힐 수 있다. 해당 날짜는 통계와 Y축 스케일에서 제외하고 "집계 시작일(기존 이용자 일괄 반영)" 주석을 표시한다 [미결: 실제로 발생하는지, 날짜].

완료 기준
- [ ] 화면 어디에도 "가입자"라는 단어가 없다(용어집 기준).
- [ ] 휴면 비율과 구성 막대의 값이 카드 값과 일치한다.
- [ ] 휴일 제외 토글 시 막대·평균이 바뀌고 누적선은 그대로다.

### 11.5 체류시간 (P0)

**설명 한 줄**: 그날 사용자들의 평균 체류시간. (산출 방식 한 줄은 자리표시 문구로 두고 담당자가 수정: "세션 기준으로 …")
**데이터**: `UsageInsights_Daily(@metric='stay_time')`. 일별 평균 체류시간(초), 선택적으로 중앙값(초), 그날의 이용자 수, 휴일 정보.

- DAU 화면과 같은 구성이다: 필터(기간, 휴일 제외 기본 ON, 7일 이동평균), 카드, 평균선이 있는 라인 차트, 줌, 표.
- 표시 단위는 분(소수 1자리)이며 서식은 `formatDuration` 한 곳에서 관리한다. 기간 평균은 "일별 평균의 단순 평균"이라고 (?)에 밝힌다.
- 중앙값이 오면 차트에 보조선으로 표시한다(없으면 숨김). 툴팁과 표에는 그날의 이용자 수를 함께 표시해서 표본 크기를 알 수 있게 한다.
- 표 컬럼: 날짜, 요일, 평균 체류시간(분), 중앙값(분, 있을 때), 이용자 수, 휴일. 숫자는 우측 정렬, 최신순, 전체 행이다.

완료 기준
- [ ] DAU 화면의 완료 기준 중 공통 항목이 모두 동일하게 동작한다.
- [ ] 중앙값 컬럼이 없어도 오류 없이 표시된다.

### 11.6 기능별 사용현황 (P0)

**데이터**: `UsageInsights_Features(@view='list')`(기능 ID, 이름(ko/en), 사용자 수, 조회 수, 이전 기간 값), `UsageInsights_PeriodSummary`(도달률 분모). 기능 상세도 같은 `UsageInsights_Features`를 `@view='summary'/'daily'/'departments'/'top_users'`로 호출한다(§13). 기간은 기본 1년이며 기간 합산형 조회에서는 오늘을 제외한다(C10). 상세 일별 조회는 오늘 행을 집계중으로 표시할 수 있다(C7~C9).

**목록 화면**
- 필터: 기간. 정렬 세그먼트 컨트롤(1클릭 전환): **사용자 수(기본) | 조회 수 | 증감**. 열 머리를 눌러도 정렬된다. [미결: "사용자수 조회수 기준보다 더 중요하다"를 "사용자 수가 조회 수보다 중요"로 해석함]
- **순위 보기**: 가로 막대 차트(기본 Top 10, "더 보기"로 전체) + 옆에 숫자 표(순위, 기능명, 사용자 수, 조회 수, 도달률, 사용자당 조회 수, 이전 기간 대비). 기능명은 최대 30자이므로 말줄임 + 툴팁이다. 표에 검색 상자를 둔다.
- **분포 보기**(P1): 산점도(x=사용자 수, y=조회 수, 점 클릭=기능 선택). 조회는 많지만 소수가 쓰는 기능 / 넓게 쓰이지만 얕은 기능을 구분하는 용도다.
- 지표: 도달률 = 기능 사용자 수 ÷ 기간 전체 이용자 수, 사용자당 조회 수 = 조회 수 ÷ 사용자 수. (?)에 정의를 표시한다.

**기능 상세** (`/features/:featureId`, 목록에서 선택하면 우측 패널로 열리고 URL이 바뀌어 공유 가능)
- 요약: 사용자 수, 조회 수, 도달률, 최초 사용일, 최근 사용일, **신규 사용자 / 재사용자 비율**(기간 내 이 기능을 처음 쓴 사람 vs 이전에도 쓴 사람)
- 일별 추이: 사용자 수 선 + 조회 수 막대(휴일 제외 옵션, 평균선)
- **부서별 분포**: 부서별 사용자 수 막대
- **상위 사용자** Top 10(이름, 부서, 사용일수, 조회 수): `usage.users.view` 권한이 있을 때만 표시. 행 클릭 시 유저 상세로 이동
- 상세 패널의 각 영역은 독립적으로 로딩된다.

완료 기준
- [ ] 정렬 전환이 1클릭이며 선택한 기준의 열이 강조된다.
- [ ] 30자 기능명이 레이아웃을 깨지 않는다(말줄임 + 툴팁).
- [ ] 권한이 없으면 "상위 사용자" 영역이 보이지 않고, 직접 API 호출도 403이다.
- [ ] 기능 선택 URL을 공유하면 같은 기능 상세가 열린다.
- [ ] 사용자 수 합계가 전체 이용자 수와 다를 수 있다는 설명이 있다.

### 11.7 유저별 사용현황 (P0, 권한 `usage.users.view`)

**데이터**: `UsageInsights_Users(@view='list')`(사용자별 사용일수, 조회 수, 사용 메뉴 수). 유저 상세도 같은 `UsageInsights_Users`를 `@view='summary'/'daily'/'features'`로 호출한다(§13). 순위는 프론트에서 계산한다(전체 목록 1회 조회 후 정렬 기준 전환 시 재조회 없음).

**순위 화면**
- 필터: 기간, 정렬 세그먼트 컨트롤 **사용일수(기본) | 조회 수 | 사용 메뉴 수** (중요도 순). 클릭 한 번으로 바뀌고 기준 열이 강조된다.
- **순위 규칙** [제안]: 선택한 기준으로 내림차순, 동점이면 나머지 기준을 (사용일수 → 조회 수 → 사용 메뉴 수) 순으로 비교한다. 모든 기준이 같으면 공동 순위(1, 2, 2, 4)이다. 순위는 항상 전체 사용자 기준이다.
- 컬럼: 순위 | 이름 | 부서 | ID | 사용일수 | 조회 수 | 사용 메뉴 수. 이름은 충분히 넓게(외국인 긴 이름 대비, 말줄임 + 툴팁), 부서는 이름보다 좁아도 되지만 긴 부서명을 위해 말줄임 + 툴팁, ID는 고정폭 글꼴이다. 사용자의 유일 키는 ID이며 동명이인은 ID로 구분한다.
- **기본 Top 10**, "50명 / 100명 / 전체" 전환(가상 스크롤로 끝까지 볼 수 있음).
- **검색**: 이름·ID·부서를 검색한다. 결과에는 **전체 기준 순위**가 표시된다(필터링해도 순위는 바뀌지 않음). 부서 필터(`dept`)를 지원한다.
- **내 행**을 하이라이트하고 "내 사용현황" 바로가기를 제공한다(로그인 ID = 유저 ID [미결: 두 값의 동일 여부]). 기간에 사용 기록이 없으면 안내 문구를 보인다.
- (?)로 정의: 사용일수 = 하루에 몇 번을 써도 1일로 센 횟수(얼마나 자주), 조회 수 = 조회 버튼을 누른 횟수, 사용 메뉴 수 = 사용한 서로 다른 기능의 수(얼마나 다양하게).

**유저 상세** (`/users/:userId`, 행 클릭 시 우측 패널 또는 페이지, URL 공유 가능)
- 헤더: 이름, 부서, ID
- 요약: 기간 내 사용일수 / 조회 수 / 사용 메뉴 수와 각각의 **순위(N위 / 전체 M명)**, 첫 접속일(전체 이력), 마지막 접속일, **최장 연속 사용일**(휴일은 연속을 끊지 않음, 기간 내)
- **캘린더 히트맵**(GitHub 스타일, 일별 조회 수, 휴일은 빗금 패턴). 한 열 = ISO 주, **월요일이 맨 위**(WAU 주 단위와 일치)
- 일별 사용 추이 차트
- **기능별 사용 분포**: 기능별 사용일수·조회 수(막대)
- 상단 안내 배너(§5) 표시

**부서별 요약** (`/departments`, P1, `usage.view`): 부서별 활성 이용자 수, 조회 수, (부서 인원수가 있으면) 보급률 = 활성 이용자 ÷ 인원수. 부서를 클릭하면 유저 순위가 `dept`로 필터링된다(권한이 있는 경우).

완료 기준
- [ ] 정렬 기준 전환이 1클릭이고 기준 열이 강조된다.
- [ ] 이름·부서 검색 결과에 전체 순위가 그대로 표시된다.

## 12. API 명세

접두어 `/api/v1`. 모든 엔드포인트는 인증 필수이고 (권한, Site) 검사를 거친다. 조회 파라미터는 `from`, `to`(YYYY-MM-DD)이며 기능/유저 대상은 경로에 둔다.

**API는 기존 구분을 유지한다.** SP는 내부 저장·조회 구현이며 API와 1:1일 필요가 없다. 일별 지표와 상세 영역은 반환 모델·권한·로딩 및 재시도 단위가 다르므로 각 API가 명확한 계약을 갖도록 한다. 특히 기능 상위 사용자 조회는 별도 권한이 필요하다. 내부 SP 통합은 §13의 매핑으로 흡수하며, 클라이언트에 SP 조회 유형을 그대로 노출하는 범용 엔드포인트로 합치지 않는다.

| 메서드 · 경로 | 설명 | 권한 |
|---|---|---|
| `GET /me` | 사용자 정보(이름·부서·ID), 유효 권한, 접근 가능 Site, 서버 capabilities(`dataSourceSwitch` 등) | 로그인 |
| `GET /sites` | 접근 가능 Site 목록(이름, 타임존, 오늘, data_start_date) | 로그인 |
| `GET /sites/{site}/usage/freshness` | 데이터 기준 시각 | `usage.view` |
| `GET /sites/{site}/usage/dau` | 일별 DAU | `usage.view` |
| `GET /sites/{site}/usage/active-users/rolling` | 롤링 MAU·WAU | `usage.view` |
| `GET /sites/{site}/usage/active-users/calendar?unit=week\|month` | 캘린더 주/월 | `usage.view` |
| `GET /sites/{site}/usage/user-base/summary` | 누적·90/180/365일 | `usage.view` |
| `GET /sites/{site}/usage/new-users/daily` | 일별 신규 | `usage.view` |
| `GET /sites/{site}/usage/stay-time/daily` | 일별 체류시간 | `usage.view` |
| `GET /sites/{site}/usage/period-summary` | 기간 요약(전체 이용자 수 등) | `usage.view` |

| `GET /sites/{site}/usage/features/{id}/summary` `/daily` `/departments` | 기능 상세 | `usage.view` |
| `GET /sites/{site}/usage/features/{id}/top-users` | 기능 상위 사용자 | `usage.users.view` |
| `GET /sites/{site}/usage/departments` | 부서별 요약 | `usage.view` |

- 기간 합산형은 `to`를 어제로 자른 값으로 SP를 호출하고, 실제 사용한 `to`를 `meta`에 담는다. 통합 후에는 SP 이름이 아니라 §13.2의 조회 유형별로 적용하며, 기능·사용자 상세의 `daily` 조회에는 이 자르기를 적용하지 않는다. 기능 목록의 이전 기간 비교값은 백엔드가 `compare_from`/`compare_to`를 계산해서 SP에 전달한다.
- 프론트에는 `name_i18n`이 적용된 형태로 내려준다. SP 컬럼명 그대로 노출하지 않는다.
- 클라이언트 요청 헤더 `X-Data-Source: mock|real`은 `ALLOW_DATA_SOURCE_SWITCH=true`이고 `admin` 권한일 때만 유효하다. 아니면 무시한다.

## 13. SP 명세 초안

`docs/SP_SPEC.md`로 정식화하고, 담당자가 실제 SP를 만들 때 기준으로 삼는다. 아래 규칙을 벗어나야 하면 구현 에이전트가 임의로 바꾸지 말고 질문한다.

### 13.1 통합 기준과 반환 원칙

현재 범위의 물리 SP는 **18개 → 8개**로 통합한다. API와 Provider의 논리 조회는 유지하고, 같은 업무 대상·조회 패턴을 다루는 SP에 조회 유형 파라미터를 추가한다.

- 일별 DAU·신규 이용자·체류시간: `UsageInsights_Daily`의 `@metric`으로 구분한다.
- 롤링·캘린더 활성 이용자: `UsageInsights_ActiveUsers`의 `@basis`로 구분한다.
- 기능 목록·상세 4종: `UsageInsights_Features`의 `@view`로 구분한다.
- 사용자 목록·상세 3종: `UsageInsights_Users`의 `@view`로 구분한다.
- `UserBase`는 한 기준일의 누적·최근 N일 현황, `PeriodSummary`는 임의 기간의 고유 이용자·조회 합계이므로 별도로 유지한다. 부서 집계와 데이터 갱신 정보도 각각 독립된 조회 책임을 유지한다.
- **호출 한 번은 선택한 조회 유형의 결과 집합 하나만 반환한다.** 선택한 분기만 실행하고, 다른 유형의 데이터까지 계산하거나 여러 결과 집합을 일괄 반환하지 않는다. 화면 영역별 독립 로딩·취소·캐시를 유지한다.
- **조회 유형에 따라 결과 컬럼은 달라도 되지만, 동일한 SP + 조회 유형의 컬럼명·타입·NULL 허용 여부는 고정한다.** 빈 목록도 같은 컬럼 구조의 0행 결과를 반환한다. 모든 유형을 하나의 넓은 NULL 컬럼 테이블이나 JSON 문자열로 합치지 않는다.
- 통합은 SP 관리 단위를 줄이는 결정이다. API 요청 수나 DB 실행 횟수가 자동으로 줄어드는 것은 아니다. 성능은 조회 유형별 실행 계획과 응답시간으로 검증한다.

### 13.2 공통 규칙

- 4개 Site DB에 **같은 SP 이름·파라미터·조회 유형별 결과 계약**으로 배포한다. 백엔드는 중앙 SQL Server의 동일한 연결 설정을 사용하고, Site는 SP 파라미터가 아니라 §6의 Linked Server·DB 매핑으로 구분한다. 아래 SP 이름 앞에 해당 Site의 `[linked_server].[database].[schema]`를 붙여 호출한다(§4).
- 날짜 파라미터와 결과는 `date` 타입이며 해당 Site 현지 날짜 기준이다. 시각 컬럼은 타임존 없는 `datetime`(현지 시각)이다.
- 일별 조회는 **조회 기간의 모든 날짜를 행으로 반환**한다(이용자 0명인 날도 0으로). 정렬은 날짜 오름차순이다. 이 규칙은 통합 SP의 일별 분기에도 동일하게 적용한다.
- 요일은 `iso_weekday tinyint`(월=1 … 일=7)로 반환하고 화면에서 언어별로 표시한다. `DATENAME`은 언어 설정 영향을 받으므로 쓰지 않는다. 계산식: `DATEDIFF(day, '19000101', @d) % 7 + 1`
- **[H]** 휴일 컬럼 세트: `is_holiday bit NOT NULL`, `holiday_name_ko/en/zh nvarchar(100) NULL`(`_zh`는 예약: 이번 범위에서는 NULL이어도 되며 앱이 쓰지 않는다. 나중에 중국어 UI를 추가할 때 SP 계약을 바꾸지 않기 위함 [제안]). 공휴일 + 회사 휴일을 반영하며, 토·일 여부는 Site 캘린더가 결정한다(SP가 판단).
- **[N(x)]** 이름 컬럼 세트: `x_name_ko/en/zh nvarchar(200) NULL`(`_zh`는 [H]와 같이 예약). 비어 있으면 앱이 대체 규칙을 적용한다.
- 카운트는 `int`, 비율은 앱에서 계산한다. 결과 컬럼은 snake_case이다.
- 일별·롤링 조회의 오늘 값과 캘린더 조회의 진행 중인 주·월은 집계중 값을 반환할 수 있다. 앱이 집계중 표시와 통계 제외를 적용한다(§9.2, §11.3).
- 기간 합산형 조회는 앱이 잘라서 준 `@to_date`(어제 이하)까지만 계산한다. **SP 이름이 아니라 조회 유형 기준**으로 적용한다. `Features`의 `list`/`summary`/`departments`/`top_users`, `Users`의 `list`/`summary`/`features`, `Departments`, `PeriodSummary`가 대상이다. `Features`·`Users`의 `daily`는 오늘 행을 허용한다.
- 조회 유형은 아래에 명시한 값만 허용한다. 필수 파라미터 누락, 알 수 없는 유형, 사용하지 않는 파라미터의 비NULL 값, 잘못된 날짜 범위를 SP에서도 검증하고 오류로 처리한다. 누락된 ID를 전체 조회로 해석하지 않는다.
- SP는 `SET NOCOUNT ON`을 사용하고, 허용된 유형을 명시적인 분기로 처리한다. 사용자 입력으로 SP 이름·테이블명·SQL 구문을 조합하지 않는다.

### 13.3 SP 목록 (현재 범위: 8개)

표의 필수 파라미터에는 기본값을 두지 않는다. 선택 파라미터는 기본 `NULL`이며, 아래 조건부 규칙을 적용한다. 날짜 파라미터는 모두 `date`다.

| # | SP | 필수 파라미터 | 선택 파라미터 | 조회 유형 / 역할 |
|---|---|---|---|---|
| 1 | `UsageInsights_Daily` | `@metric varchar(20)`, `@from_date`, `@to_date` | 없음 | `dau`, `new_users`, `stay_time` |
| 2 | `UsageInsights_ActiveUsers` | `@basis varchar(10)`, `@from_date`, `@to_date` | `@unit char(1)` | `rolling`, `calendar` |
| 3 | `UsageInsights_UserBase` | `@as_of_date` | 없음 | 기준일(어제)의 누적·최근 90/180/365일 이용자 |
| 4 | `UsageInsights_PeriodSummary` | `@from_date`, `@to_date` | 없음 | 기간 내 고유 이용자·조회 합계 |
| 5 | `UsageInsights_Features` | `@view varchar(20)`, `@from_date`, `@to_date` | `@feature_id varchar(50)`, `@compare_from`, `@compare_to`, `@top int` | `list`, `summary`, `daily`, `departments`, `top_users` |
| 6 | `UsageInsights_Users` | `@view varchar(20)`, `@from_date`, `@to_date` | `@user_id` | `list`, `summary`, `daily`, `features` |
| 7 | `UsageInsights_Departments` | `@from_date`, `@to_date` | 없음 | 부서별 이용 현황 |
| 8 | `UsageInsights_Freshness` | 없음 | 없음 | 데이터 집계 기준일·마지막 갱신 시각 |

**조건부 파라미터 규칙**

- `ActiveUsers`: `rolling`이면 `@unit`은 NULL. `calendar`이면 `@unit='W'` 또는 `'M'` 필수. API의 `unit=week/month`를 Provider가 `W/M`으로 변환한다.
- `Features`: `list`이면 `@feature_id`는 NULL. 나머지 유형은 `@feature_id` 필수.
- `Features.list`: `@compare_from`/`@compare_to`는 둘 다 유효한 날짜이거나 둘 다 NULL이다. 백엔드가 C18에 따라 이전 기간을 계산하며, 비교 불가능하면 둘 다 NULL로 전달하고 `prev_users`/`prev_views`도 NULL로 반환한다. 다른 유형에서는 비교 파라미터를 둘 다 NULL로 전달한다.
- `Features.top_users`: `@top`은 양의 정수이며 생략하면 10이다. Provider는 기본값을 적용한 `@top=10`을 전달하고 SP도 NULL이면 10으로 처리한다. 다른 유형에서는 `@top`이 NULL이어야 한다.
- `Users`: `list`이면 `@user_id`는 NULL. 나머지 유형은 `@user_id` 필수. ID의 SQL 타입·길이는 실제 사용자 ID 계약에 맞춰 `SP_SPEC.md`에서 확정하고 모든 사용자 조회에서 통일한다.
- `UserBase`: 백엔드가 Site 현지 어제를 `@as_of_date`로 전달한다. 최근 N일의 범위는 `[as_of−N+1, as_of]`다.

**백엔드 연결·권한·캐시**

- 각 API는 권한·Site 검사를 마친 후 고정된 논리 조회를 호출한다. API의 Site를 서버 설정의 Linked Server·DB·스키마로 해석하고 중앙 연결에서 원격 SP를 실행한다. 클라이언트가 Linked Server·DB·SP 이름이나 내부 조회 유형을 임의로 지정하는 범용 API는 만들지 않는다.
- `Features.top_users`는 같은 SP의 다른 분기와 달리 `usage.users.view` 권한과 접근 기록이 필요하다. `Users`의 모든 분기도 같은 권한·접근 기록을 적용한다. SP 실행 권한만으로 사용자별 화면 접근을 허용하지 않는다.
- SP 내부에는 조회 유형별 SELECT와 명시적인 결과 컬럼을 둔다. Provider는 `SP + 조회 유형`에 해당하는 모델로 결과를 검증하고 기존 API 응답으로 변환한다. MockProvider도 같은 논리 조회·응답 계약을 따른다.
- 캐시와 single-flight 키는 `source + site + 호출 대상 + 정규화한 전체 파라미터`다. 실데이터의 호출 대상은 Linked Server·DB·스키마·SP이며, mock은 외부 DB 없이 Site와 논리 조회를 구분한다. 조회 유형, 단위, 날짜, 대상 ID, 비교 기간, `@top`을 포함한다. 예를 들어 같은 기간의 `Features.list`와 `Features.top_users`, 또는 서로 다른 Site가 캐시를 공유하면 안 된다. 기본값과 NULL도 일관되게 정규화한다.
- 로그에는 request_id와 함께 논리 조회, SP 이름, 조회 유형, 소요시간을 남겨 통합 후에도 느린 분기를 식별할 수 있게 한다. 사용자 ID는 기존 접근 기록 정책을 따른다.

### 13.5 후속 후보 (P2, 현재 8개에 포함하지 않음)

리텐션과 월 사용일수 분포는 집계 축과 입력 계약이 달라 별도 후보로 유지한다. 이번에는 명세만 정의하며 실제 SP 구현 대상이 아니다.

| SP | 파라미터 | 결과 |
|---|---|---|
| `UsageInsights_RetentionCohorts` | `@from_date`, `@to_date`, `@unit` | `cohort_start`, `cohort_size`, `period_offset`, `retained_users` |
| `UsageInsights_ActiveDaysDistribution` | `@month_start` | `bucket`, `users` |

`docs/SP_SPEC.md`에는 **SP + 조회 유형별로** 결과 컬럼(타입, NULL 여부, 정렬), 샘플 결과 3~5행, 빈 결과·잘못된 파라미터 처리, 성능 유의점(인덱스 후보)을 채운다. 물리 SP가 8개여도 기존 18개 논리 조회의 계약과 검증 범위는 유지한다.

## 14. 가상 데이터 명세

목적: 화면 설계를 실제와 비슷한 데이터로 검증하고, 실데이터 연결 전에 SP 계약을 확정한다.

- **이벤트 시뮬레이션에서 모든 값을 파생한다.** 사용자 로스터(수천 명)와 (사용자, 날짜, 기능, 조회) 이벤트를 시드 고정으로 한 번 만들고, DAU·WAU·MAU·신규·누적·기능별·유저별 값을 전부 그 이벤트에서 계산한다. 값이 서로 자연스럽게 맞고, 공유 링크가 항상 같은 화면을 보여준다. 시뮬레이션은 날짜의 함수이며 "지금 시각"에 의존하지 않는다(오늘 집계중 값만 예외).
- 규모(가정): `KR1` DAU 100~150 · WAU 300~500 · MAU 1000~1500, `KR2`·`CN1`·`US1`은 더 작게. Site별로 규모·휴일·패턴을 다르게 한다.
- 패턴: 평일 높고 주말·휴일 급락, 명절 연휴 저조, 여름·연말 소폭 저조, 완만한 성장, 이상치 몇 개(장애일 등).
- 휴일: Site별 달력(한국 명절·개천절·한글날·선거일·회사 휴일, 중국 春节·国庆 + **조정근무일(주말인데 근무일)**, 미국 Thanksgiving·Christmas + 회사 휴무). 휴일명은 ko/en으로 넣는다.
- 신규: 로그 시작 직후 4~6주는 기존 사용자가 신규로 잡혀 높게 시작해서 감쇠한다(§11.4 주석 처리 검증용).
- 마스터 데이터: 기능 20~35개(영문 3자 약어 ~ 30자 이름 포함, 인기도는 편중), 부서 15~25개(긴 이름 포함, ko/en), 사용자 이름(한국어·중국어·긴 영문 이름 혼합, 동명이인 포함).
- 체류시간: 사용자·일 단위 분포(로그정규)에서 평균 산출, 방치 이상치 소수 포함(중앙값 검증용).
- 오늘: Site 현지 오늘의 값은 하루 중 경과 비율만큼의 집계중 값으로 만든다.
- 개발용 환경변수: `MOCK_LATENCY_MS_MIN/MAX`(기본 300~1200ms, 로딩·취소 UI 검증용), `MOCK_FAIL_RATE`(오류 UI 검증용). 로스터·이벤트 생성은 Site별 첫 요청 시 지연 생성 + 메모리 캐시이며 5초 이내여야 한다.
- **불변조건은 테스트로 고정한다**: DAU ≤ WAU(롤링) ≤ MAU(롤링) ≤ 누적, 90일 ≤ 180일 ≤ 365일 ≤ 누적, 누적의 증가분 = 신규 합, 기능별 사용자 수 ≤ 기간 이용자 수, 유저별 사용일수 합·조회 합이 일별·기능별 합과 일치, 같은 파라미터는 같은 결과.

## 15. 테스트·완료 기준

**프론트 단위 테스트 (Vitest)**: 날짜 유틸(프리셋, 월말 보정, 윤년, ISO 주 라벨·연도 경계), 날짜 표시 형식(3종 서식·입력 해석·잘못된 입력 거부·자동 매핑), 기간 팝오버(적용 전에는 조회하지 않음, 이전/다음 기간 경계), 기간 포함 규칙(§11.3), 통계(오늘·휴일 제외, 빈 데이터, 최대·최소 날짜), 이동평균, 휴일 제외 시리즈 생성(방식 B), 순위 계산(동점·공동 순위), URL 상태 직렬화/복원, 이름 대체 규칙, CSV 생성(BOM), 이전 기간 계산.

**백엔드 테스트 (pytest)**: 모든 엔드포인트의 권한 × Site 매트릭스, 파라미터 검증, 오늘 계산(Site 타임존), 기간 합산형의 `to` 자르기, single-flight·캐시·타임아웃 매핑, 가상 데이터 불변조건, Provider 인터페이스 계약 테스트(Mock과 Mssql이 같은 스키마를 반환하는지, Mssql은 SP 결과를 흉내낸 fixture로 검증).

- **통합 SP 계약 검증**: 기존 18개 논리 조회가 모두 API → Provider → SP·조회 유형으로 매핑되는지 확인한다. 조회 유형별 고정 스키마·빈 결과, 필수/조건부 파라미터, 잘못된 유형 거부, `@top` 기본값, 비교 기간 NULL 처리를 검증한다.
- **통합에 따른 경계 검증**: 같은 SP의 서로 다른 조회 유형·대상·단위가 캐시와 single-flight를 공유하지 않는지, 합산형과 `daily`의 오늘 처리 차이가 유지되는지 확인한다. 권한 없는 기능 상위 사용자 조회는 SP 호출 전에 차단되고, 일반 기능 조회로 내부 유형을 바꿔 우회할 수 없어야 한다.
- **Linked Server 경로 검증**: 4개 Site가 같은 중앙 연결 설정을 사용하면서 각자의 4부분 SP 이름으로 매핑되는지 확인한다. 권한 없는 Site·등록되지 않은 Site는 DB 호출 전에 거부한다. 설정 식별자 인용과 값 파라미터 바인딩, Site 간 캐시 분리, 한 Site 오류 시 다른 Site로 대체하지 않는 동작을 검증한다.
- 실제 DB 연결 전에는 SP 결과 fixture와 호출 파라미터로 검증한다. 실제 SP 배포 후에는 담당자가 각 분기의 결과 집합이 하나인지, 스키마가 고정인지, 파라미터 검증과 성능이 계약에 맞는지 확인한다.
- 실데이터 연결 시 담당자는 실제 앱용 중앙 DB 계정으로 4개 Site의 원격 호출을 검증한다. `RPC OUT`, 로그인 매핑·원격 EXECUTE 권한, 연결/조회 타임아웃, autocommit 호출, Site별 타임존 및 중앙 서버를 통한 동시 조회 부하를 확인한다.

**화면 검증 (화면을 바꿀 때마다)**

단위 테스트와 콘솔 오류 확인은 화면이 깨지지 않았다는 증거가 아니다. 화면 변경마다 아래를 직접 확인한다(스크린샷 또는 브라우저).

- 범위: 바꾼 화면 + 바꾼 공용 컴포넌트(헤더, 사이드바, 필터 바, 표, 차트 프레임, 설정 창 등)를 쓰는 화면
- 열리는 요소는 연 상태로 본다: 설정 창, 기간 선택 팝오버, 상세 패널, 사용자 메뉴, 툴팁
- 조합 (최소)
  - 언어: ko, en 둘 다 (en이 대체로 더 길다)
  - 테마: Indigo + 형태가 다른 테마 1종 이상(예: Graphite 또는 Midnight). 테마 토큰을 바꿨다면 6종 전부
  - 날짜를 표시하는 화면이면 날짜 형식 `YYYY-MM-DD`와 `MM/DD/YYYY`
  - 폭: 1440px, 1280px, 1024px 미만(사이드바 드로어)
- 세로는 스크롤 끝까지 본다. 첫 화면만 보고 끝내지 않는다.
- 점검 항목
  - 의도하지 않은 줄바꿈(버튼 묶음, 탭, 배지, 라벨)
  - 말줄임 때문에 뜻을 알 수 없게 된 문구
  - 같은 줄·같은 묶음 요소의 높이·폭 불일치(카드, 버튼)
  - 겹침, 화면 밖으로 잘림, 의도하지 않은 가로 스크롤
  - 숫자 우측 정렬과 숫자·문자 컬럼 간격(C28)
  - 로딩·빈 데이터·오류 상태
- 결과 보고: 확인한 조합, 발견한 문제와 처리 결과(수정함 / 남김 + 이유)

4. MAU/WAU의 롤링/캘린더 토글은 두 차트 공용
5. 캘린더 MAU/WAU는 조회 기간에 완전히 포함되는 주·월 + 진행 중인 주·월만 표시
6. 기간 합산형 조회(기능·유저·부서)는 오늘을 제외하고 어제까지로 호출
7. 유저 순위는 선택 기준 → 나머지 기준 순으로 동점 해소, 모두 같으면 공동 순위
8. 최장 연속 사용일은 휴일을 끊지 않는 영업일 기준
9. 개요의 DAU 카드는 "가장 최근 영업일" 값
10. 설정은 1차 localStorage, 인터페이스로 분리해서 서버 저장 전환 가능
11. `usage.users.view` 호출 접근 기록 + 안내 배너
12. 데이터 소스 전환은 `admin` + 서버 허용 시에만 노출
13. 고착도 차트에만 휴일 제외 토글(기본 ON)
14. 체류시간은 SP가 초 단위로 주고 화면은 분 단위(소수 1자리)로 표시
15. BFF 방식 OIDC(백엔드가 세션 관리)
16. SP의 `_zh` 이름 컬럼은 예약으로 유지(이번 범위에서는 사용하지 않음)
